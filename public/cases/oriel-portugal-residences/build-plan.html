01

Before anything is built

The outcome, the entry points and every way a buyer’s story ends.

Why plan first

Three platforms make it easy to lose track of which flow does what. This page names the outcome of each one before n8n, Make or Zapier is opened.

Outcome

Every viewing request is confirmed within one working day with an architect and a slot, every email to the studio reaches the person who should answer it, and an architect approves anything Claude drafts for a buyer’s inbox.

Entry points

Five entry points: the viewing form, the studio inbox, a new revision in Airtable, n8n’s own Error Trigger and a webhook that Make and Zapier report failures to.

Every way a job ends

  • Reserved
  • Not now
  • Care request with the team
  • Flagged for a person

Out of scope

  • Reservations, contracts and deposits
  • The models themselves and the headsets’ setup
  • Construction and site scheduling
  • The Residence Q&A bot and the agents, planned on their own page
02

Naming convention

One vocabulary across n8n, Make and Zapier.

Why it matters

Three platforms, one studio. When a run fails, its name has to say which flow it was, wherever it ran.

Rule of thumb

If a run log does not read like a sentence, rename the steps.

Workflows

OR-[number] · [Title]
OR-01 · Private viewing
OR-H02 · Log a failed run

The same codes on every platform. The number is the build order; helpers get an H.

Steps

[Verb] [object]
Match the architect
Hold a viewing
Log the buyer

Default names like “HTTP Request1” or “Router 2” never survive a build.

Webhook paths

/or/[source]
/or/viewing
/or/failed

One path per source, all lowercase.

Connections

OR · [Service] ([platform])
OR · HubSpot (n8n)
OR · HubSpot (Make)
OR · Gmail (Zapier)

Each platform holds its own connection, and the name says which one to renew.

HubSpot properties

oriel_[noun], snake_case, _at for times
oriel_residence
oriel_walked_at

One prefix keeps Oriel’s own fields apart from HubSpot’s.

Airtable tables

Title case, one thing per table
Projects
Duty rota
Revisions

Flows read fields by name, never by position.

OR-01n8n

Private viewing

17 nodes, 3 decisions.

Watch for

  • The confirmation is a fixed template, so it goes out without waiting for a person. Claude’s line only ever reaches the architect.
  • The form asks no time, so the flow holds the first free slot from the next working day, and the buyer can move it.
  • Cal.com’s own confirmation email is turned off for the viewing event types, so the buyer gets one email, Oriel’s.
  • With no free slot, the flow stops with an error instead of guessing. OR-H02 tells the studio, who reply by hand within the working day.
  • Buyers are matched on email, never on name.
  • In n8n, a search that finds nothing ends the run quietly. Every search here has Always Output Data on: a first-time buyer goes on with an empty history, and a missing architect makes the slot request fail, so OR-H02 tells the studio.
  • The courier, not the form, asks a home buyer for their address.

Outcome

Every viewing request has an architect, a ninety-minute slot and a confirmation within one working day, and a home viewing has its headset on the way.

Trigger

The private viewing form on the site posts to /or/viewing.

Exits

  • Viewing confirmed at the studio
  • Viewing confirmed, headset on its way
  • Stopped, no free slot
OR-02Make

Studio inbox

16 nodes, 3 decisions.

Watch for

  • Nothing here writes back to the sender. Every reply is a person’s.
  • If Claude’s answer cannot be read, the error route resumes with Not sure, so the email is flagged, never lost.
  • Every module that writes has an error route that posts to /or/failed and ends in Break, so Make keeps the run to retry.
  • Not sure is the router’s fallback route, so an email that matches no filter still lands with a person.
  • In Make, a search that matches nothing returns no bundle and ends its route, so a router after it never runs. The owner and supplier lookups use Airtable’s Make an API call instead: it always returns one bundle with a records list, and the router counts it, so an unmatched owner or an unnamed residence is flagged, never silently dropped.

Outcome

Every email to studio@oriel.pt reaches the person who should answer it, and every buyer lands in HubSpot.

Trigger

Make’s Gmail module checks studio@oriel.pt every 15 minutes.

Exits

  • Buyer in HubSpot, task for sales
  • Care request opened
  • Founders told
  • Forwarded to a site team
  • Added to hiring
  • Labelled Check
OR-03Zapier

Model revision notice

11 nodes, 1 decision.

Watch for

  • No revision note reaches a buyer before the project architect answers. An unanswered request sends nothing.
  • Human in the Loop sends no Telegram message itself. It notifies the reviewer with the link to its Zapier-hosted page, so the Telegram Bot steps before it only say a note is waiting; the page does not exist until Human in the Loop runs.
  • Human in the Loop’s own choices are Approved or Rejected; Rejected is read as Rewrite, so the branch still reads Approve or Rewrite, as on the Automation page.
  • Zapier paths never join again, so both paths call the same Sub-Zap, OR-H03, and the send is built once.
  • The note never promises a date or a price.
  • A failed step is caught by a Zapier Manager zap that posts it to OR-H02.

Outcome

Everyone who walked a residence hears, in plain words, what changed in its model, and only after its architect has read the note.

Trigger

Zapier sees a new record in the Revisions table in Airtable.

Exits

  • Sent as Claude wrote it
  • Sent as the architect rewrote it
  • Nobody to tell
  • Waiting on the architect
05

Helpers

Three small workflows the others call.

Why helpers

Alerts and failures are written once, in n8n, and all three platforms report to them. OR-H03 exists because Zapier paths never join again.

OR-H01 · Alert the studio

Every message to the studio reads the same way and lands in one Telegram chat.

OR-H02 · Log a failed run

Every failed run, on any of the three platforms, is logged and reaches the studio with a link to it.

OR-H03 · Send a revision note

One place sends a revision note and logs it, whichever path approved it.

07

Build order

Five phases, in the order they are built.

Order

Foundation first, then one platform at a time, in the order a buyer meets them: the viewing, the inbox, then the revisions.

  1. 1 · Foundation

    • Create the Viewings pipeline, its stages and the oriel_ properties in HubSpot
    • Create the Airtable tables: Projects, Duty rota, Revisions, Handover, Care requests, Hiring
    • Add the connections on each platform: OR · HubSpot, OR · Gmail, OR · Airtable, OR · Anthropic, OR · Telegram
    • Create the Sheets tabs: Failed runs, Test matrix
    • Build OR-H01 in n8n, then OR-H02 with OR-01 (not OR-H01) as the covered error workflow

  2. 2 · Viewings on n8n

    • Set up each architect’s Studio viewing and Home viewing event types in Cal.com, with their own confirmation email turned off
    • Agree the booking details for the headset courier
    • Build OR-01 and point the site’s viewing form at /or/viewing
    • Run tests t01–t05

  3. 3 · Inbox on Make

    • Build OR-02 with its router, six kind routes and the two lookup branches, on a test mailbox
    • Give every module that writes an error route to /or/failed
    • Run tests t06–t14

  4. 4 · Revisions on Zapier

    • Build OR-H03 as a Sub-Zap, then OR-03 with its Telegram notices and two paths
    • Add the Zapier Manager zap that posts failures to /or/failed
    • Run tests t15–t18 with a test residence and test contacts

  5. 5 · Test and hand over

    • Point OR-02 at studio@oriel.pt
    • Run the whole matrix again with the real architects and a real headset delivery
    • Walk Inês, Tomás and the architects through the handover page
    • Turn every flow on
08

Handover

What the studio keeps.

Written for the studio

One page, no jargon, for Inês, Tomás and the architects. It lives next to the flows.

What it does

  • Confirms every viewing request within one working day, with an architect and a ninety-minute slot.
  • Books the headset courier for every home viewing.
  • Sorts every email to studio@oriel.pt and hands it to the person who answers it.
  • Puts every buyer in HubSpot, whether they used the form or wrote.
  • Drafts a plain note when a model changes, and sends it only after the architect approves.

What breaks it

  • Renaming a field in the Projects or Revisions table in Airtable.
  • Adding a residence without its architect and Cal.com user in Projects.
  • Changing the viewing form’s questions or answers on the site.
  • Changing an architect’s Cal.com event types.
  • Renaming the Viewings pipeline or its stages in HubSpot.
  • A connection expiring on one platform but not the others.

Who to call

Justine Acosta, who built it. Failures already reach the studio’s Telegram group with a link to the run.

Where the logs are

Every failed run, from any of the three platforms, is a row in the Failed runs tab and a Telegram message. Every viewing and every buyer email is on the buyer’s HubSpot timeline.
