# Site Chat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A small floating chat on every page that answers questions from the site's own content with Claude Haiku 5.5 and hands interested visitors to the existing contact form, prefilled.

**Architecture:** `lib/chat/knowledge.ts` turns the chosen `data/` modules plus a digest of `data/cases` into one deterministic text block, sent as a cached system prompt by `POST /api/chat`. That route streams plain text back. A client hook keeps the conversation in `sessionStorage`, and a launcher and panel in `components/chat/` render it. The hand-off writes the visitor's questions to `sessionStorage` for `ContactForm` to pick up.

**Tech Stack:** Next 16 route handlers, React 19, Tailwind 4, `@anthropic-ai/sdk`, Vitest + Testing Library, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-11-site-chat-design.md`

## Global Constraints

- Model `claude-haiku-5-5`, exactly. No other model, no date suffix.
- Haiku 5.5 thinks by default and thinking tokens count toward `max_tokens`. Send `output_config: { effort: 'low' }` and `max_tokens: 1000`, and leave `thinking` unset. This replaces the spec's "max_tokens about 400": reply length is held by the prompt's 2–4 sentence rule.
- SDK client: built once, `timeout: 20_000`, `maxRetries: 0`. `export const maxDuration = 30` on the route.
- Limits: 20 chat messages per IP per hour; at most 10 visitor turns (1–19 entries, alternating, starting and ending on `user`); visitor message ≤ 500 characters, assistant message ≤ 2,000.
- Knowledge block ≤ 160,000 characters (40k tokens at characters ÷ 4).
- Hand-off marker is the literal `[[contact]]`.
- Server-only `ANTHROPIC_API_KEY`. Only a boolean `enabled` ever reaches the browser.
- All visitor-facing text lives in `data/chat.ts`. Storage keys live in `lib/storage-keys.ts`.
- Every `sessionStorage` read and write is wrapped in try/catch, and the feature works with storage throwing.
- Never stage or commit `data/about.ts`: it holds Justine's uncommitted edits from `feat/about-copy`. Stage files by name, never `git add -A` or `git add .`.
- Comment style follows the repo: a short `/** … */` per export saying what it is for.
- Don't bring back any of the removed assistant's subsystems: no Supabase, no keyless quick answers, no in-chat form, no fake mode in production code.

## Review Focus

1. **A partly streamed `[[contact]]`:** mid-stream the visible text may end in `[[`, `[[con`, and so on. The visitor should never see marker fragments. Pinned in Task 2 (`splitReply` partial cases).
2. **Links the model invents:** a reply might link to `https://evil.example`, `javascript:…` or a path that doesn't exist. Only paths that appear in the knowledge block should render as links; anything else stays plain text. Pinned in Task 2 (`parseLinks`).
3. **A forged history:** a hand-crafted POST could send assistant turns that claim things, or 19 entries of 2,000 characters. These are capped and validated, and the route never trusts the order. Pinned in Task 3 (validation cases).
4. **Storage unavailable** (private mode, blocked site data): the chat still works for the tab's lifetime, and the hand-off still navigates (the form is just empty). Pinned in Tasks 4 and 5 (storage throwing).
5. **Multi-turn with thinking on:** earlier assistant turns are sent back as plain text with no thinking blocks. If the API rejects that, the second turn breaks. Pinned in Task 8 (`chat-check` runs one two-turn conversation and fails loudly on a non-200).
